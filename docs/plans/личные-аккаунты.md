# Личные аккаунты и подготовка «Зачёта» к публикации

Статус: в работе, версия 0.2 от 6 ноября 2026 года. Шаги 1–5 выполнены: 32 локальные проверки прошли, шаги 1–4 проверены на Windows и Linux. В браузере проверены вход, регистрация, восстановление черновика и смена аккаунта между вкладками; форма помещается на ширине 320, 390 и 1440 пикселей. Далее — подготовка запуска на сервере.

Связано: [описание проекта](../../README.md), [API](../../Program.cs), [модели](../../Models.cs), [интерфейс](../../wwwroot/app.js), [проверки](../../tests/test_api.py), [GitHub Actions](../../.github/workflows/check.yml).

## Идея

Сделать версию, в которой два студента пользуются одним сервером, а каждый видит только свои предметы и задания. После этого подготовить запуск по HTTPS с постоянной базой и резервной копией. Это следующий законченный этап; напоминания и вложения идут после него.

Сейчас `Program.cs` возвращает общий список данных, а `Models.cs` не хранит владельца. Открывать такую версию для нескольких пользователей рано: сначала нужно разделить данные и проверить все операции с чужими записями.

## Решения по умолчанию

| Вопрос | Решение для версии 0.2 |
| --- | --- |
| Сервер и интерфейс | Сохранить ASP.NET Core 10, SQLite и текущие HTML, CSS, JavaScript |
| Учётные записи | ASP.NET Core Identity; адрес электронной почты и пароль |
| Вход в браузере | Cookie с `HttpOnly` и `SameSite=Lax`; в размещённой версии только HTTPS и `Secure` |
| Срок входа | 7 дней без автоматического продления |
| Пароль | От 12 до 128 символов; без обязательного набора знаков, цифр и регистра; хеширование средствами Identity |
| Ошибки входа | После 5 неудачных попыток заблокировать вход в аккаунт на 15 минут; общий ответ о неверных данных |
| Частота запросов входа и регистрации | Не больше 10 запросов за минуту с одного адреса; превышение — `429` |
| Регистрация | В локальной разработке включена; в Production по умолчанию выключена через `Accounts:AllowRegistration` |
| Чужая запись | Ответ `404`; списки содержат только собственные записи |
| Предметы с одинаковым названием | Разрешены у разных владельцев; запрещены у одного, независимо от регистра |
| Старые данные | Только явный перенос в выбранный аккаунт; не отдавать первому зарегистрировавшемуся |
| База | Сохранить SQLite; один экземпляр приложения и постоянная папка данных |
| Восстановление пароля | Через почту пока не реализовывать; на странице входа не показывать неработающую ссылку |

Адрес почты в этом этапе служит именем для входа. Подтверждение адреса и отправка писем не входят в версию 0.2. Роли, общие группы, JWT и отдельный frontend-фреймворк пока не нужны.

## Порядок работ

Задачи 1–4 выполнять последовательно. Задача 5 завершает проверку всей версии; задачу 6 начинать после неё. В процессе сохранять текущие проверки и добавлять новые к соответствующему изменению.

### Задача 1: обновление схемы базы через миграции

**Файлы:** `Program.cs`, `StudyTracker.csproj`, `.config/dotnet-tools.json`, `Migrations/`, `tests/test_api.py`, `start.ps1`, `README.md`.

1. Добавь `Microsoft.EntityFrameworkCore.Design` и локальный инструмент `dotnet-ef` версии 10.0.14, согласованной с текущим EF Core.
2. Создай первую миграцию для существующей схемы.
3. Замени `EnsureCreated` явной командой приложения `--migrate`. При обычном старте проверяй готовность схемы; при неприменённых миграциях заверши запуск с понятным сообщением.
4. Обнови скрипт запуска: сначала применяй миграции, затем запускай приложение. В тестовом окружении выполняй ту же команду перед сервером.
5. Если найдена старая база без истории миграций, не меняй её. Сообщи, как создать новую папку данных и позже перенести записи по задаче 3.

**Тесты:** `test_migrations_create_empty_database` — таблицы созданы, списки пусты; `test_migrations_are_repeatable` — повторный запуск возвращает код `0` без потери записей; `test_legacy_database_is_not_modified` — запуск отклонён, содержимое старой базы не изменилось.

**Проверка:** `dotnet tool restore`, `dotnet build --nologo`, `python tests/test_api.py`. Ожидается успешная сборка, прежние 7 сценариев и новые проверки миграций без ошибок.

**Коммит:** `Добавлены миграции и явное обновление базы`.

### Задача 2: регистрация, вход и выход

**Файлы:** `StudyTracker.csproj`, `Models.cs`, `Program.cs`, новые `AuthEndpoints.cs`, `Migrations/`, `appsettings.json`, `tests/test_api.py`.

1. Добавь пакет Identity для EF Core той же версии 10.0.14 и пользователя на основе `IdentityUser`.
2. Настрой cookie, правила пароля, блокировку и ограничение частоты запросов по таблице выше.
3. Реализуй только нужные маршруты: `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`.
4. Используй `UserManager` и `SignInManager`; не сохраняй и не проверяй пароли собственным кодом. После регистрации предложи вход, не создавай сеанс автоматически.
5. Сохрани `/api/token` для получения токена защиты. Проверяй токен на регистрации, входе и выходе; после смены пользователя выдавай новый токен.
6. Добавь настройку закрытой регистрации для Production. Не записывай пароли, cookie и токены в журнал.

**Тесты:** `test_registration_and_login` — регистрация `201`, вход `200`, `/api/auth/me` возвращает текущий аккаунт; `test_logout_ends_session` — после выхода `/api/auth/me` возвращает `401`; `test_short_password_is_rejected` — 11 символов отклоняются, 12 допустимых принимаются; `test_login_is_locked_after_five_failures` — правильный пароль не открывает сеанс во время блокировки; `test_auth_requires_csrf` — запрос без токена получает `400`; `test_registration_can_be_disabled` — новый аккаунт не создаётся; `test_auth_rate_limit` — 11-й запрос в пределах минуты получает `429`.

Для проверки блокировки и лимитов используй отдельное окружение, чтобы предыдущие сценарии не расходовали их пороги.

**Проверка:** `dotnet build --nologo`, `python tests/test_api.py`. Ожидается, что пароль в базе представлен хешем, а сеанс определяется cookie. Проверить `Secure` отдельно при запуске по HTTPS; локальные HTTP-тесты этого не подтверждают.

**Коммит:** `Добавлены регистрация и вход через ASP.NET Core Identity`.

### Задача 3: собственные предметы и задания у каждого пользователя

**Файлы:** `Models.cs`, `Program.cs`, `Migrations/`, новый `LegacyImport.cs`, `tests/test_api.py`, `README.md`.

1. Добавь владельца предмета и задания. Для предмета замени уникальный индекс `NameKey` на составной индекс владельца и `NameKey`.
2. Свяжи задание с предметом того же владельца: проверяй это в API и закрепи составным внешним ключом в базе.
3. Закрой все маршруты предметов и заданий требованием входа. Владельца определяй по текущему аккаунту; не принимай его из тела запроса.
4. Ограничь владельцем каждую выборку, изменение, удаление и проверку существования предмета. На чужой идентификатор возвращай `404`.
5. Добавь отдельную команду `--import-legacy <путь> --owner <почта>`. Открывай исходную базу только для чтения; требуй существующий аккаунт с пустым списком предметов и заданий. Переноси записи в одной транзакции с сохранением описаний, сроков, статусов и даты создания. При ошибке отменяй перенос целиком.
6. При повторном переносе в уже заполненный аккаунт заверши команду кодом `1`. Не удаляй исходную базу и не запускай перенос автоматически.

**Тесты:** `test_anonymous_cannot_access_assignments` — `401` с корректным токеном защиты для изменяющих запросов; `test_users_see_only_own_records` — у двух пользователей разные списки; `test_foreign_assignment_cannot_be_changed_or_deleted` — `404`, исходная запись не меняется; `test_foreign_subject_cannot_be_used` — `404`, задание не создаётся; `test_same_subject_name_for_different_users` — оба создания получают `201`, повтор у одного владельца — `409`; `test_legacy_import_preserves_records` — количество, сроки и статусы совпадают; `test_legacy_import_rejects_nonempty_owner` — код `1`, новые дубли не появились.

**Проверка:** `dotnet build --nologo`, `python tests/test_api.py`. Ожидается, что ни один сценарий с аккаунтом А не читает и не меняет данные аккаунта Б. Для переноса использовать только временную базу с заранее известными данными.

**Коммит:** `Предметы и задания разделены по владельцам`.

### Задача 4: формы входа и работа с истёкшим сеансом

**Файлы:** `wwwroot/index.html`, `wwwroot/app.js`, `wwwroot/app.css`, `tests/test_api.py`.

1. Добавь формы входа и регистрации в текущем оформлении. При закрытой регистрации показывай только вход.
2. Перед загрузкой заданий запрашивай `/api/auth/me`; без сеанса показывай вход и не загружай личные списки.
3. После входа обновляй токен защиты и загружай данные; после выхода очищай списки и состояние фильтров в памяти браузера.
4. При ответе `401` снова показывай вход. Если пользователь редактировал задание, сохрани черновик только в памяти вкладки и предложи восстановить его после повторного входа в тот же аккаунт. При смене аккаунта удали черновик.
5. Добавь кнопку выхода, сообщения о неверном пароле, блокировке и потере связи. Не выводи пользователю сырые ответы Identity.
6. Проверь клавиатуру, видимый фокус и ширину 320, 390 и 1440 пикселей.

**Тесты:** в API сохрани `test_logout_ends_session` и добавь `test_login_rotates_csrf_identity` — старый анонимный токен после входа отклоняется, новый работает. В браузере проверь цепочку «регистрация → вход → своё задание → выход → другой аккаунт»: чужая карточка не появляется даже на время загрузки.

**Проверка:** `node --check wwwroot/app.js`, `python tests/test_api.py`; затем проверка в браузере. Ожидается отсутствие горизонтальной прокрутки, доступность форм с клавиатуры и понятное восстановление после `401`.

**Коммит:** `Добавлены формы входа и управление сеансом в интерфейсе`.

### Задача 5: проверки всей версии на GitHub

**Файлы:** `tests/test_api.py`, `.github/workflows/check.yml`, `README.md`.

1. Раздели тестовые HTTP-клиенты и cookie для двух пользователей. Токен защиты получай заново после каждого входа и выхода.
2. Сохрани проверки сроков, трёх статусов, удаления и перезапуска из первой версии; выполняй их с авторизованным клиентом.
3. Добавь проверку повторного входа после перезапуска сервера и сохранности данных обоих владельцев.
4. Запускай восстановление локальных инструментов, сборку и полный набор сценариев на Windows и Linux.
5. В README укажи фактически проверенные сценарии и ограничения версии, убери устаревшее описание общего списка заданий.

**Тесты:** `test_two_users_survive_restart` — оба аккаунта входят после перезапуска, у каждого прежние записи; `test_cross_account_csrf_is_rejected` — чужая пара токена и cookie получает `400`. Все ранее перечисленные проверки остаются обязательными.

**Проверка:** `dotnet tool restore`, `dotnet build --nologo`, `node --check wwwroot/app.js`, `python tests/test_api.py`; затем оба задания GitHub Actions должны завершиться успешно. Точное количество тестов обновить по результату, не заявлять его заранее.

**Коммит:** `Проверены личные аккаунты на Windows и Linux`.

### Задача 6: подготовка запуска на сервере

**Файлы:** новые `Dockerfile`, `.dockerignore`, `compose.yaml`, `Caddyfile`, `tests/test_deployment.py`, `docs/запуск-на-сервере.md`; существующие `Program.cs`, `appsettings.json`, `.gitignore`, `README.md`.

1. Собери приложение в многоэтапном Docker-образе на .NET 10. Запускай рабочий процесс без прав root.
2. Вынеси SQLite и ключи ASP.NET Core Data Protection в отдельные постоянные тома. Не клади их в образ и Git.
3. Добавь отдельную команду обновления базы перед запуском приложения. Не запускай миграции конкурентно из нескольких процессов.
4. Добавь `/health` без личных данных. Настрой Caddy для HTTPS и передачу заголовков только от известного прокси.
5. Подготовь резервное копирование: остановка приложения, копирование базы и ключей, возобновление работы. Проверяй восстановление в отдельные тома, не поверх рабочей базы.
6. Опиши команды запуска, обновления и восстановления. Оставь регистрацию выключенной по умолчанию.
7. Фактическое размещение выполняй после выбора сервера и домена. Платные ресурсы на этапе составления плана не создавать.

**Тесты:** `test_health_returns_200` — сервер отвечает `200` без личных данных; `test_container_restart_preserves_data` — записи остаются после пересоздания контейнера; `test_cookie_survives_container_restart` — сохранённые ключи позволяют продолжить сеанс в пределах 7 дней; `test_backup_restore_preserves_records` — восстановлены оба аккаунта и их задания. До публикации вручную проверь HTTPS и атрибут `Secure` у cookie.

**Проверка:** `docker compose config`, `docker compose build`, `python tests/test_deployment.py`. Ожидается запуск тестового окружения, успешные проверки и удаление только тестовых контейнеров и томов. Команды для настоящего домена уточнить в `docs/запуск-на-сервере.md` после его выбора.

**Коммит:** `Подготовлен запуск с HTTPS и постоянным хранением данных`.

## Когда версия готова

- Два аккаунта работают на одном сервере и не видят данные друг друга.
- Проверки чужих идентификаторов проходят для чтения списков, создания, изменения и удаления.
- Вход, выход, блокировка и защита от поддельных запросов проверены.
- Обновление схемы и перенос старой базы обходятся без удаления исходных данных.
- Сборка и тесты проходят на Windows и Linux.
- Есть проверенный способ сохранить и восстановить базу; перезапуск не теряет записи.
- Формы работают на телефоне и с клавиатуры. Проверка настоящего телефона отмечена отдельно от проверки узкого окна браузера.
