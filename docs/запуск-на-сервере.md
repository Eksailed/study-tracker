## Как это работает

Один сервер запускает приложение и Caddy. Снаружи доступны только порты 80 и 443 Caddy; порт 8080 приложения не публикуется. Caddy получает сертификат для выбранного домена и передаёт запросы в приложение. ASP.NET Core принимает заголовки адреса клиента и HTTPS только от заданного адреса Caddy.

Образ приложения работает от пользователя `app` без прав root. Перед запуском отдельный сервис `migrate` обновляет схему; при ошибке приложение не стартует. SQLite остаётся базой для одного экземпляра приложения. Несколько экземпляров приложения одновременно здесь не предусмотрены.

| Том при имени проекта `zachet` | Содержимое |
| --- | --- |
| `zachet_data` | SQLite: `tracker.db` и служебные файлы |
| `zachet_keys` | Ключи Data Protection для cookie и токенов защиты |
| `zachet_caddy_data` | Сертификаты и служебные данные Caddy |
| `zachet_caddy_config` | Служебная конфигурация Caddy |

Ключи приложения должны сохраняться вместе с базой. Имя приложения Data Protection закреплено как `Zachet`, поэтому пересоздание контейнера не завершает действующие сеансы. Копии с ключами храни вне репозитория с доступом только у владельца сервера.

## Что нужно для настоящего размещения

- Linux-сервер с Docker Engine и Docker Compose.
- Домен с DNS-записью на адрес сервера. Если есть запись IPv6, она тоже должна вести на этот сервер.
- Открытые входящие TCP-порты 80 и 443; исходящий доступ Caddy к центру сертификации.
- Свободная подсеть Docker, по умолчанию `172.30.0.0/24`.

Покупка сервера и домена в этот этап не входит. Команды ниже выполняются на уже выбранном сервере из папки проекта.

## Первый запуск

```sh
git clone https://github.com/Eksailed/study-tracker.git
cd study-tracker
cp .env.example .env
```

В `.env` задай `DOMAIN` без `https://`, пути и порта. Например, свой домен вместо `study.example.com`. Если подсеть уже используется, согласованно измени `BACKEND_SUBNET`, `BACKEND_POOL` и `PROXY_IP`: адрес прокси должен входить в подсеть и находиться вне пула динамических адресов. `172.30.0.2` и `172.30.0.128/25` уже разделены.

```sh
docker compose -p zachet config --quiet
docker compose -p zachet build
docker compose -p zachet run --rm migrate
docker compose -p zachet run --rm --no-deps app --create-account student@example.com
docker compose -p zachet up -d
docker compose -p zachet logs --tail 50 app caddy
```

Команда создания аккаунта запросит пароль со скрытым вводом: от 12 до 128 символов. Пароль не передаётся аргументом и не записывается в файл. Это позволяет оставить регистрацию в браузере закрытой. Повторная команда с той же почтой завершается ошибкой и не меняет пароль существующего аккаунта.

Чтобы пользоваться группами, назначь владельца: `docker compose -p zachet run --rm --no-deps app --make-owner student@example.com` (аккаунт должен уже существовать; команда написана по `compose.yaml` и в контейнере не запускалась).

Открой `https://<свой домен>`. Маршрут `/health` должен вернуть `{"status":"ok"}`; после входа должны быть доступны только задания своего аккаунта. Настоящий сертификат появляется после корректной настройки домена и доступности портов, а не при создании репозитория.

Для `localhost` Caddy использует свой локальный центр сертификации. Автоматические проверки доверяют его сертификату только внутри своего процесса Python и не меняют доверенные сертификаты Windows или браузера.

## Обновление

1. Сохрани резервную копию по инструкции ниже и останови приложение.
2. Выполни `git pull --ff-only` и `docker compose -p zachet build`.
3. Примени схему командой `docker compose -p zachet run --rm migrate`.
4. Запусти `docker compose -p zachet up -d`.
5. Проверь `/health`, вход, список заданий и журнал приложения.

Если миграция завершилась ошибкой, не запускай старую версию поверх частично изменённой базы. Сохрани журнал и восстанавливай согласованную копию приложения, базы и ключей. Для старой общей базы используется [явный импорт](../README.md#перенос-старой-базы); автоматического назначения владельца нет.

## Резервная копия

Следующие команды предназначены для shell Linux. Они используют имя проекта `zachet`, заданное при первом запуске.

```sh
docker compose -p zachet stop app
backup_dir="$PWD/backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
docker run --rm --network none -v zachet_data:/source:ro -v "$backup_dir:/backup" alpine:3 tar -C /source -czf /backup/data.tar.gz .
docker run --rm --network none -v zachet_keys:/source:ro -v "$backup_dir:/backup" alpine:3 tar -C /source -czf /backup/keys.tar.gz .
docker compose -p zachet start app
```

Остановка перед копированием сохраняет согласованное состояние SQLite, включая файлы WAL. Папка `backups` исключена из Git. После создания перенеси копию в отдельное хранилище. Для сохранения сертификатов Caddy можно также скопировать `zachet_caddy_data`, предварительно остановив Caddy.

## Копия командой приложения

Команда `--backup` делает копию без остановки приложения: снимок SQLite берётся средствами самой базы, поэтому он согласован, даже если приложение пишет. Рядом копируются ключи Data Protection, а копия базы проверяется `PRAGMA integrity_check`. Если проверка не прошла, файл копии удаляется, команда завершается с кодом `1`. Токены API лежат в базе и сохраняются вместе с ней. Старые копии команда не удаляет.

Запуск через сервис `migrate` (в нём уже подключены тома `data` и `keys`; команда из `compose.yaml` заменяется аргументами):

```sh
mkdir -p backups
sudo chown 1654:1654 backups
docker compose -p zachet run --rm -T -v "$PWD/backups:/backup" migrate --backup /backup
```

Три оговорки:

- **Папка для копий.** Её нужно примонтировать отдельно (`-v …:/backup`): в `compose.yaml` её нет. Контейнер работает от пользователя `app` (в образах .NET это `1654`), поэтому папке на сервере нужны права записи для него; команда `chown` выше даёт их. Без прав команда напишет ошибку и завершится с кодом `1`.
- **Схема базы.** Команда сама не обновляет схему: если после `git pull` миграции не применены, она откажет. Сначала выполни `docker compose -p zachet run --rm migrate`.
- **Результат.** Команда печатает пути: `tracker-ГГГГММДД-ЧЧммсс.db` и папку ключей `tracker-ГГГГММДД-ЧЧммсс-keys` в том же месте. Для восстановления нужны обе.

Пример `cron` для копии каждую ночь в 03:00 (под пользователем, который состоит в группе `docker`; журнал пишется в файл):

```cron
0 3 * * * cd /opt/study-tracker && docker compose -p zachet run --rm -T -v /opt/study-tracker/backups:/backup migrate --backup /backup >> /var/log/zachet-backup.log 2>&1
```

Ночью приложение работает как обычно. Копии не удаляются сами: раз в месяц убирай старые вручную или отдельным заданием. Копию стоит переносить в отдельное хранилище.

## Восстановление в отдельный проект

Не распаковывай архивы поверх рабочей базы. Пример ниже создаёт новые тома. Сначала задай `backup_dir` абсолютным путём к выбранной копии и проверь наличие обоих архивов.

```sh
docker volume create zachet-restore_data
docker volume create zachet-restore_keys
docker run --rm --network none -v zachet-restore_data:/target -v "$backup_dir:/backup:ro" alpine:3 tar -C /target -xzf /backup/data.tar.gz
docker run --rm --network none -v zachet-restore_keys:/target -v "$backup_dir:/backup:ro" alpine:3 tar -C /target -xzf /backup/keys.tar.gz
```

### Восстановление командой `--restore`

Команда кладёт базу и ключи из копии в **пустую** папку данных. Если там уже есть `tracker.db`, она откажет с кодом `1` и ничего не изменит: рабочую базу команда затереть не может. Новый проект Compose создаёт свои пустые тома:

```sh
docker compose -p zachet-restore run --rm -T -v "$backup_dir:/backup:ro" migrate --restore /backup/tracker-20261109-030000.db
docker compose -p zachet-restore run --rm migrate
docker compose -p zachet-restore up -d
```

Имя файла подставь своё; папка ключей `tracker-20261109-030000-keys` должна лежать рядом. Если копия сделана старой версией приложения, `migrate` приведёт схему к текущей. Аккаунты, задания и токены API вернутся вместе с базой, а сеансы продолжат работать благодаря сохранённым ключам.

Для проверки на том же сервере исходный проект нужно остановить командой `docker compose -p zachet down` **без `--volumes`**: рабочие тома останутся, а порты и подсеть освободятся. Затем запусти `docker compose -p zachet-restore up -d` и проверь вход обоих пользователей, количество предметов, задания, сроки и статусы. Для параллельной проверки нужны отдельные порты, подсеть и домен.

Обычная остановка и обновление не должны удалять тома. Автоматический сценарий восстановления использует только случайные имена `zachet-test-*` и удаляет именно свои временные контейнеры и тома.

## Мониторинг и журнал

- `GET /health` — «жив»: всегда `200 {"status":"ok"}`, без проверок.
- `GET /health/ready` — «готов»: открывает базу, сверяет применённые миграции с известными, проверяет запись в папку ключей. Если всё в порядке, отвечает `200`, иначе `503` и JSON с именами проверок (`database`, `schema`, `keys`) и `ok`/`fail`. Поле `telegram` только сообщает `disabled`, `ready` или `error` и на код ответа не влияет. Тексты исключений и пути в ответ не попадают, подробности пишутся в журнал. Этот адрес подходит для внешнего мониторинга; в `compose.yaml` проверка не добавлялась, потому что в образе нет `curl`.
- В Production журнал выводится JSON-строками в консоль контейнера (`docker compose -p zachet logs app`). На каждый запрос пишется одна строка: метод, путь без query, статус, длительность в миллисекундах и номер запроса. `/health` и `/health/ready` в журнал не попадают.
- Тот же номер приходит в заголовке ответа `X-Request-Id`: если пользователь сообщил об ошибке, найди по этому номеру строки журнала одного запроса. Заголовок `Authorization`, токены (`zt_…` и токен Telegram), пароли и query в журнал не попадают.

## Проверка перед размещением

```sh
docker compose config --quiet
docker build -t study-tracker:local .
python tests/test_deployment.py
```

Проверки запускают настоящий HTTPS через Caddy. Они создают два аккаунта при закрытой регистрации, проверяют cookie с `Secure`, работу без root, пересоздание приложения и восстановление данных и ключей в другом проекте. Проверка сертификата включена; отключение TLS-проверки не используется.

Проверки настоящего домена, внешнего DNS и доступа с реального телефона выполняются после выбора инфраструктуры. Успешный локальный HTTPS сам по себе их не подтверждает.

Основа настройки: [доверенные прокси ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/proxy-load-balancer?view=aspnetcore-10.0), [автоматический HTTPS Caddy](https://caddyserver.com/docs/automatic-https).
