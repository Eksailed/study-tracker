# Эксплуатация и API: готовность, журнал, копии, токены, документация

Статус: идея, спецификация от 9 ноября 2026 года для версии 0.5. Дизайн согласован в чате, сама спецификация ждёт проверки. Ничего не собиралось и не запускалось: числа и имена — решения по умолчанию, а подводные камни (разбор `Authorization` вместе с cookie, `OpenAPI` в .NET 10) выведены из чтения кода и проверяются на первых тестах. Работа идёт сразу в `main`, после каждой задачи — коммит и push.

Связано: [README](../../README.md), [запуск на сервере](../запуск-на-сервере.md), [тесты на C#](тесты-на-csharp.md), [аккаунты](../../AuthEndpoints.cs), [эндпоинты заданий](../../Endpoints/AssignmentEndpoints.cs), [защитные заголовки](../../SecurityMiddleware.cs), [командная строка](../../CommandLine.cs), [CI](../../.github/workflows/check.yml).

## Идея

Сейчас «Зачёт» умеет жить на сервере, но сопровождать его неудобно, а внешним приложениям он закрыт:

- `/health` отвечает «ok», даже если база недоступна;
- журнал стандартный, номера запроса в нём нет;
- резервная копия — ручное копирование `App_Data`, команды для неё нет;
- API работает только по cookie с CSRF-токеном, то есть из браузера;
- описания API нет.

В версии 0.5 добавляем пять вещей: проверку готовности, журнал с номером запроса, команды `--backup` и `--restore`, токены доступа для чужих приложений и документацию API. Интерфейс на `/api` не меняется. Существующее поведение не ломается.

## Что не входит

- OAuth, обновление токенов, вход через сторонние сервисы.
- Самостоятельная регистрация приложений: токен выпускает сам пользователь в своём аккаунте.
- Вебхуки и подписки на изменения.
- Метрики Prometheus и панели мониторинга.
- Автоматическое расписание копий и удаление старых копий: копию делает команда, расписание задаёт администратор (`cron`, планировщик Windows).
- Доступ токена к уведомлениям, аккаунту и настройкам: токену доступны только предметы и задания.
- Новые поля заданий и предметов.

## Решения по умолчанию

| Вопрос | Решение |
| --- | --- |
| Кто пользуется токеном | Чужие приложения: у токена есть название, области и отзыв по каждому |
| Области | `tasks:read` и `tasks:write`, независимые; запись не даёт чтение |
| Формат токена | `zt_` и 43 символа base64url из 32 случайных байт |
| Хранение | В базе только SHA-256 токена и первые 8 символов для опознания; сам токен показывается один раз |
| Срок | По умолчанию 90 дней, максимум 365, минимум 1 день |
| Число токенов | Не больше 10 действующих на аккаунт |
| Лимит запросов | 120 в минуту на токен, дальше `429` и `Retry-After` |
| Адреса | `/api/v1/subjects`, `/api/v1/assignments`; интерфейс остаётся на `/api` |
| Выпуск токенов | Только по cookie и CSRF; токеном выпускать токены нельзя |
| Документация | `/api/v1/openapi.json` (встроенный `Microsoft.AspNetCore.OpenApi`) и страница `/api/docs` без внешних библиотек |
| Формат ошибок | Как сейчас: `{"error": "текст"}` |
| Готовность | `/health/ready`, коды `200` и `503`, без текстов исключений |
| Журнал | В Production — JSON в консоль; одна строка на запрос; `/health*` не пишется |
| Копии | Онлайн-копия SQLite (`BackupDatabase`) и копия папки `keys`; проверка `PRAGMA integrity_check` |
| Восстановление | Только в пустую папку данных; в папку с базой — отказ |
| Порядок | Сначала готовность и журнал, потом копии, потом токены, потом документация |
| Ветка | Работа сразу в `main` по решению пользователя; push после каждой задачи |

## Токены доступа

### Хранение

Новая таблица `ApiTokens` и миграция `ApiTokens`:

| Поле | Тип | Что хранит |
| --- | --- | --- |
| `Id` | `int` | Ключ |
| `OwnerId` | `string` | Владелец, внешний ключ на аккаунт |
| `Name` | `string` | Название приложения, 1–60 символов |
| `Hash` | `string` | SHA-256 токена, base64; уникальный индекс |
| `Prefix` | `string` | Первые 8 символов токена, чтобы пользователь узнал токен в списке |
| `Scopes` | `int` | Битовая маска: 1 — `tasks:read`, 2 — `tasks:write` |
| `CreatedAt` | `long` | UTC, миллисекунды |
| `ExpiresAt` | `long` | UTC, миллисекунды |
| `LastUsedAt` | `long?` | Обновляется не чаще раза в 5 минут, чтобы не писать в базу на каждый запрос |
| `RevokedAt` | `long?` | Если задан, токен недействителен |

Токен сравнивается по хэшу. Пользователь видит в списке название, начало токена, области, срок, последнее использование и состояние. Удаление аккаунта удаляет его токены каскадом.

### Управление

Только по cookie и с CSRF:

| Запрос | Что делает |
| --- | --- |
| `GET /api/tokens` | Список токенов аккаунта без хэшей |
| `POST /api/tokens` | Создаёт токен: `{name, scopes: ["tasks:read", "tasks:write"], days}`; в ответе `201` и сам токен, один раз |
| `DELETE /api/tokens/{id}` | Отзывает токен (`RevokedAt`); повторный отзыв — `204`; чужой — `404` |

Ошибки: пустое название или длиннее 60 символов, неизвестная область, пустой список областей, срок вне 1–365 дней — `400`. Одиннадцатый действующий токен — `409`. Токен в запросе управления — `401`: управлять токенами можно только из браузера.

В интерфейсе появляется раздел «Доступ к API»: список, форма создания, показ нового токена с кнопкой «Скопировать» и предупреждением, что повторно он не покажется, отзыв. Выход и смена аккаунта очищают показанный токен, как уже сделано для ссылки Telegram.

### Вход по токену

Заголовок `Authorization: Bearer zt_…`. Отдельная схема аутентификации `ApiToken` рядом с cookie. Правила:

- Заголовок есть и токен не подходит (нет в базе, отозван, просрочен) — `401` и `WWW-Authenticate: Bearer`, cookie не проверяется: нельзя «доиграться» до входа по cookie, подставив мусорный токен.
- Заголовка нет — работает cookie, как раньше.
- Токен принимается только на `/api/v1/...`. На `/api/...` (кроме `/api/v1`) он не действует и даёт `401`.
- Для запросов с токеном CSRF не проверяется: у них нет cookie. Для запросов по cookie на `/api/v1` CSRF проверяется, как на `/api`.
- Область: `GET` требует `tasks:read`; `POST`, `PUT`, `DELETE` — `tasks:write`. Нет нужной области — `403`.
- Лимит 120 запросов в минуту на токен (окно 1 минута, без очереди); дальше `429` с `Retry-After` в секундах.
- Данные те же, что видит владелец: чужие записи недоступны, `OwnerId` берётся из токена, а не из тела.

## Адреса и документация

`/api/v1/subjects` и `/api/v1/assignments` вызывают те же `MapSubjects` и `MapAssignments`. Чтобы заголовок `Location` в `201` указывал на правильный префикс, оба метода принимают префикс (`/api` или `/api/v1`) параметром; поведение на `/api` остаётся прежним.

- `/api/v1/openapi.json` — описание только адресов `/api/v1` (предметы и задания) и схемы `Bearer`. Не содержит `/api/auth`, `/api/notifications`, `/api/tokens`. Доступно без входа и без токена: в нём нет данных.
- `/api/docs` — статическая страница `wwwroot/api-docs.html` и `wwwroot/api-docs.js`, которая читает `openapi.json` и показывает адреса, параметры, примеры `curl` и коды ошибок. Без внешних скриптов и CDN: заголовок CSP (`script-src 'self'`) не ослабляется.
- Единый формат ошибок `{"error": "текст"}` описан в документации; фактический формат не меняется.

## Готовность и журнал

### Готовность

`GET /health` остаётся «жив»: `200 {"status":"ok"}` без проверок. Новый `GET /health/ready` отвечает `200` или `503` и кратким JSON:

| Проверка | Что делает | Если не прошла |
| --- | --- | --- |
| `database` | Открывает базу и выполняет `SELECT 1` | `503` |
| `schema` | Сравнивает применённые миграции с известными | `503` |
| `keys` | Создаёт и удаляет временный файл в папке ключей | `503` |
| `telegram` | Только сообщает: `disabled`, `ready` или `error` | Не влияет на код ответа |

Тексты исключений и пути в ответ не попадают: только имена проверок и `ok`/`fail`. Подробности пишутся в журнал. Docker `compose.yaml` не меняется: в образе нет `curl`, а проверку делает внешний мониторинг.

### Журнал

- В Production — JSON в консоль (`AddJsonConsole`); в Development — обычный текстовый вывод.
- Одна строка на запрос: метод, путь без query, статус, длительность в миллисекундах, `X-Request-Id`. `/health` и `/health/ready` не пишутся.
- Заголовок ответа `X-Request-Id` берётся из `HttpContext.TraceIdentifier` и входит в область журнала, поэтому ошибки того же запроса связаны с ним.
- В журнал не попадают заголовок `Authorization`, токены (`zt_…` и токен Telegram), пароли и query. Это проверяется тестом.

## Резервные копии

Команды командной строки (в `CommandLine.cs`, рядом с остальными):

| Команда | Что делает |
| --- | --- |
| `--backup <папка>` | Создаёт в папке `tracker-ГГГГММДД-ЧЧммсс.db` онлайн-копией SQLite, копирует `keys/` в подпапку `tracker-ГГГГММДД-ЧЧммсс-keys`, проверяет копию `PRAGMA integrity_check`, печатает пути |
| `--restore <копия.db>` | Восстанавливает базу и ключи из пары «копия и её папка ключей» в пустую папку данных (`Tracker:DataDirectory`); печатает результат |

Правила:

- Копия делается без остановки приложения (`BackupDatabase` берёт согласованный снимок), но восстановление выполняется при остановленном приложении.
- `--restore` отказывает с кодом `1`, если в папке данных уже есть `tracker.db`: тексты ошибок по-русски, как у остальных команд. Затирать рабочую базу команда не умеет, администратор переносит её сам.
- Если `integrity_check` вернул не `ok`, копия не считается готовой: команда удаляет только что созданный файл копии и завершается с кодом `1`.
- Токены API лежат в базе и восстанавливаются вместе с ней. Ключи Data Protection копируются, чтобы действующие сеансы не пропали.
- Старые копии команда не удаляет.

В `docs/запуск-на-сервере.md` добавляются команды для Docker (`docker compose run --rm migrate --backup /backup` с тремя оговорками: том для папки, права записи, восстановление в пустой том) и расписание `cron`.

## Проверка

Тесты в `tests/StudyTracker.Tests` на xUnit:

| Класс | Что проверяет |
| --- | --- |
| `ApiTokenTests` | Выпуск, один показ, хэш в базе вместо токена, предел 10, срок, отзыв, повторный отзыв, чужой токен и чужой отзыв, запрет управления токеном, области `403`, просроченный и отозванный `401`, мусорный токен не откатывается на cookie |
| `ApiV1Tests` | Те же операции с предметами и заданиями по токену и по cookie, CSRF только для cookie, `Location` с префиксом `/api/v1`, токен на `/api` не действует, лимит `429` и `Retry-After` |
| `HealthTests` | `/health` всегда `200`; `/health/ready` — `200` на целой базе, `503` при недоступной папке ключей и при несовпадении миграций, без текстов исключений |
| `RequestLoggingTests` | `X-Request-Id`, строка запроса, `/health` не пишется, в журнале нет токена, `Authorization` и query |
| `BackupTests` | Копия открывается и содержит записи, `integrity_check`, ключи скопированы, восстановление в пустую папку возвращает аккаунт, задание и токен, отказ в непустую папку, неисправная копия не остаётся |
| `OpenApiTests` | В `openapi.json` есть адреса `/api/v1/...` и схема `Bearer`, нет `/api/auth`, `/api/tokens`, `/api/notifications` |

После каждой проверки выполняется «сломать и вернуть»: поломка рабочего кода должна окрасить тест красным, иначе тест дополняется. Глубокая защита (например, область токена и проверка владельца вместе) часто перекрывает поломку, поэтому границы проверяются отдельно.

Интерфейс проверяется в браузере вручную (создание, показ, копирование и отзыв токена, ширина 320, 390 и 1440 пикселей, клавиатура). Контейнерные сценарии в Docker проверяются, только если Docker запущен; иначе в `README` и в ответе пишется, что не запускалось.

## Риски

| Риск | Что делаем |
| --- | --- |
| Токен в заголовке и cookie одновременно ведут к разным аккаунтам | Заголовок `Authorization` главнее; при неверном токене — `401`, cookie не используется; тест |
| Токен утекает в журнал или в сообщение об ошибке | Журнал пишет путь без query и не пишет заголовки; тест ищет `zt_` и значение токена во всём выводе |
| Лимит токенов обходится сменой токена | Лимит считается на токен, плюс общий предел 10 токенов на аккаунт |
| `LastUsedAt` пишет в базу на каждый запрос | Обновление не чаще раза в 5 минут |
| `OpenAPI` в .NET 10 показывает внутренние адреса | Описание строится только для группы `/api/v1`; тест проверяет состав |
| Копия делается во время записи | `BackupDatabase` берёт согласованный снимок; тест копирует во время открытого соединения |
| Восстановление затирает рабочую базу | Команда отказывает, если `tracker.db` уже есть; перенос рабочей базы остаётся действием администратора |
| Миграция ломает действующую базу версии 0.4 | Тест проверяет, что аккаунт и задание из схемы 0.4 переживают миграцию `ApiTokens` |

## Готово, когда

- Токен выпускается, показывается один раз, работает на `/api/v1` с нужными областями и отзывается; чужой, просроченный и отозванный токены получают `401` или `403`.
- `/health/ready` честно отвечает `200` или `503` и не раскрывает исключения.
- В журнале есть `X-Request-Id`, и нет токенов, паролей и query.
- `--backup` создаёт проверенную копию, `--restore` возвращает аккаунт, задание и токен в пустую папку и отказывает в непустую.
- `/api/v1/openapi.json` и `/api/docs` открываются без входа и без внешних скриптов.
- `dotnet build --nologo` без ошибок, `node --check` для всех файлов JavaScript и `dotnet test tests/StudyTracker.Tests` проходят; число проверок и время записаны в `README` как есть.
- Что не запускалось (например, Docker), прямо написано в `README`.
