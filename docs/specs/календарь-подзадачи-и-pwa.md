# Календарь, подзадачи и приложение на телефоне

Статус: в работе, версия 0.7, спецификация от 9 ноября 2026 года. Ничего ещё не собрано и не проверено. Дальше план `docs/plans/календарь-подзадачи-и-pwa.md`. После исполнения сюда добавятся пометки, что собрано и проверено, а что нет (настоящий телефон в этой версии проверить нечем).

## Идея

В «Зачёте» уже есть задания, напоминания в Telegram и импорт из Obsidian. Не хватает трёх вещей, которые нужны каждый день:

- **Календарь.** Сроки заданий должны быть видны там, куда пользователь и так смотрит: в календаре телефона или компьютера. Для этого у каждого аккаунта появляется адрес-лента в формате `.ics`, на который подписывается любой календарь.
- **Подзадачи и важность.** Лабораторная — это обычно несколько шагов («теория», «расчёты», «отчёт»). К заданию добавляются шаги с галочками и три уровня важности.
- **Приложение на телефоне.** «Зачёт» можно поставить на главный экран как приложение: свой значок, окно без адресной строки.

Три части независимы друг от друга и делаются отдельными задачами. Порядок: приложение, календарь, подзадачи.

## Что не входит

- Запись событий в календарь пользователя: лента только читается календарём.
- Время и напоминания внутри событий календаря: событие занимает весь день срока, будильников в нём нет.
- Работа без сети: приложение сохраняет только оболочку, данные не кэшируются, без сети виден экран «Повторить подключение».
- Push-уведомления браузера (напоминания остаются в Telegram).
- Правка подзадач токеном API: через `/api/v1` подзадачи и важность только читаются.
- Подзадачи в импорте из Obsidian и в напоминаниях Telegram.
- Вложенные подзадачи, сроки и описания у подзадач.
- Автоматическая смена статуса задания по галочкам подзадач.

## Решения по умолчанию

| Вопрос | Решение |
|---|---|
| Что открывает ленту | Отдельная ссылка-секрет, не токен API: токен даёт доступ к данным, а ссылку календари передают в адресе, и она может осесть в журналах |
| Секрет ленты | 32 случайных байта, 43 символа base64url; в базе только SHA-256 |
| Сколько лент на аккаунт | Одна; новая выдача отзывает старую |
| Какие задания попадают в ленту | Все невыполненные (`Todo`, `InProgress`), в том числе просроченные; выполненные из ленты исчезают |
| Событие | Весь день срока; название «Предмет: Название»; описание не включается |
| Статус задания при галочках | Не меняется; когда отмечены все шаги, предлагаем завершить задание |
| Важность по умолчанию | «Обычный» |
| Что кэширует приложение | Только оболочку: `index.html`, стили, скрипты, иконки |
| Порядок загрузки оболочки | Сначала сеть, при сбое кэш; поднимать версию кэша вручную не нужно |

## Приложение на телефоне (PWA)

Что добавляется в `wwwroot/`:

| Файл | Зачем |
|---|---|
| `manifest.webmanifest` | Название «Зачёт», `lang: ru`, `start_url: "/"`, `display: standalone`, цвета, иконки 192 и 512 пикселей |
| `icon-192.png`, `icon-512.png` | Значки приложения, нарисованы по `favicon.svg` |
| `apple-touch-icon.png` | Значок для главного экрана iPhone, 180 пикселей |
| `sw.js` | Сервис-воркер в корне, чтобы область действия была весь сайт |
| `pwa.js` | Регистрирует воркер, если браузер его поддерживает |

В `index.html` добавляются `<link rel="manifest">`, `<link rel="apple-touch-icon">`, `<meta name="theme-color">` и скрипт `pwa.js`.

Как работает воркер:

- Запросы `GET` к файлам оболочки и к странице `/`: сначала сеть, при сбое сети — копия из кэша. Каждый удачный ответ обновляет копию.
- Всё остальное воркер не трогает и не кэширует: `/api*`, `/health*`, `/calendar.ics`, любые методы кроме `GET`, чужие адреса. Данные пользователя в кэш не попадают.
- Без сети страница открывается из кэша, а запросы к `/api` падают и показывают уже существующий экран «Повторить подключение».

Заголовки безопасности (CSP) менять не нужно: воркер и манифест подпадают под `default-src 'self'`.

Установка работает на `localhost` и по HTTPS. По `http://<IP>:5184` браузеры установку не предлагают, это их ограничение. Проверка в этой версии: Edge на `localhost` (установка, запуск окном, отключение сети). iPhone и Android не проверялись.

## Календарная лента

### База

Таблица `CalendarLinks`:

| Поле | Тип | Смысл |
|---|---|---|
| `Id` | число | ключ |
| `OwnerId` | строка | владелец, уникальный индекс: одна лента на аккаунт |
| `KeyHash` | строка | SHA-256 секрета в шестнадцатеричном виде, уникальный индекс |
| `CreatedAt` | дата и время | когда выдан секрет |

Удаление аккаунта удаляет ленту каскадом.

### Управление лентой (cookie и CSRF, личный раздел `/api`)

| Метод и адрес | Что делает |
|---|---|
| `GET /api/calendar` | `{ "exists": true, "createdAt": "…" }` или `{ "exists": false }`; секрет не отдаёт |
| `POST /api/calendar` | Создаёт ленту или перевыпускает: возвращает `201` и `{ "key": "…", "createdAt": "…" }`; старый секрет перестаёт работать |
| `DELETE /api/calendar` | Выключает ленту: `204`; повторный вызов тоже `204` |

Секрет показывается один раз, потерянный восстановить нельзя, только перевыпустить. Токен API на этих адресах не принимается (`401`, как и вне `/api/v1`).

### Сама лента

`GET /calendar.ics?key=<секрет>` вне `/api`: без cookie и без CSRF, календари их не умеют.

- Неверный, пустой или отозванный ключ: одинаковый `404` без тела. Ответ не различает «нет такого ключа» и «ключ отозван».
- Лимит: 60 запросов в минуту с одного адреса, дальше `429` с `Retry-After`. Календари опрашивают раз в несколько часов, поэтому запас большой.
- Заголовки ответа: `Content-Type: text/calendar; charset=utf-8`, `Cache-Control: no-store`.
- Секрет лежит в query, потому что `RequestLogging` пишет только путь без query, а путь с секретом попал бы в журнал. Журнал доступа Caddy в поставляемом `Caddyfile` не включён; если пользователь включит его, адреса с секретом окажутся в журнале (об этом сказано в README).

Содержимое: `VCALENDAR` версии 2.0, `PRODID:-//Zachet//Study Tracker//RU`, `X-WR-CALNAME:Зачёт`, строки заканчиваются `CRLF`, длинные строки сворачиваются по 75 байт. Для каждого невыполненного задания:

```
BEGIN:VEVENT
UID:task-<Id>@zachet
DTSTAMP:<CreatedAt, UTC>
DTSTART;VALUE=DATE:20261120
DTEND;VALUE=DATE:20261121
SUMMARY:Физика: Лабораторная работа 3
END:VEVENT
```

`UID` не меняется при правках, поэтому календарь обновляет событие, а не множит. Запятые, точки с запятой, обратные косые и переводы строк в названии экранируются по RFC 5545.

### Раздел «Календарь» в интерфейсе

Кнопка «Календарь» в навигации открывает диалог по образцу «Токены API» и «Импорт»:

- Ленты нет: пояснение и кнопка «Создать ссылку».
- Лента есть: дата выдачи, предупреждение, что ссылка не показывается повторно, кнопка «Перевыпустить и отозвать старую» (с подтверждением) и «Выключить».
- После создания или перевыпуска: адрес `<origin>/calendar.ics?key=…` в поле только для чтения и кнопка «Скопировать». При закрытии диалога адрес стирается из страницы.
- Все тексты через `textContent`, без inline-скриптов и стилей. Выход из аккаунта сбрасывает состояние диалога (событие `account-cleared`).

## Подзадачи и важность

### База

Таблица `Subtasks`:

| Поле | Тип | Смысл |
|---|---|---|
| `Id` | число | ключ |
| `AssignmentId` | число | задание; каскадное удаление |
| `Title` | строка до 140 | название шага |
| `Done` | булево | галочка |
| `Position` | число | порядок внутри задания, с 0 |

В `Assignments` добавляется колонка `Priority`: 0 — «Обычный» (`Normal`), 1 — «Важный» (`Important`), 2 — «Срочный» (`Urgent`); по умолчанию 0. В JSON — строкой, как и `Status`. Миграция только добавляет таблицу и колонку, старые данные не трогает.

### Адреса личного раздела `/api` (cookie и CSRF)

Владельцем проверяется задание; чужое или несуществующее — `404`. Подзадача чужого задания — тоже `404`.

| Метод и адрес | Тело | Ответ |
|---|---|---|
| `POST /api/assignments/{id}/subtasks` | `{ "title": "…" }` | `201` и подзадача; ставится в конец |
| `PUT /api/assignments/{id}/subtasks/{subId}` | `{ "title"?: "…", "done"?: true }`, хотя бы одно поле | `200` и подзадача |
| `DELETE /api/assignments/{id}/subtasks/{subId}` | — | `204`; порядок остальных пересчитывается без дыр |
| `PUT /api/assignments/{id}/subtasks/order` | `{ "ids": [3, 1, 2] }` | `200` и список подзадач; в `ids` должны быть ровно все подзадачи задания |

Проверки: название 1–140 символов после обрезки пробелов; не больше 30 подзадач на задание (31-я — `400` «У задания не больше 30 шагов.»); `done` только булево; пустой список или чужие и повторные `id` в `ids` — `400`.

Задание теперь отдаётся с полями `priority` и `subtasks` (массив `{ id, title, done, position }` по возрастанию `position`). Создание и правка задания (`POST` и `PUT /api/assignments`) принимают `priority`; если поле не передано, при правке важность не меняется, при создании ставится «Обычный». Правка задания подзадачи не стирает.

### Токен API (`/api/v1`)

`GET` отдаёт `priority` и `subtasks`. `POST` и `PUT` принимают `priority` по тем же правилам. Адресов для подзадач в `/api/v1` нет. OpenAPI и страница `/api/docs` описывают новые поля.

### Интерфейс

- В карточке задания: значок важности (для «Обычного» значка нет), счётчик «2 из 5» при наличии шагов, раскрывающийся список шагов с галочками, полем «Добавить шаг», кнопками «вверх», «вниз», «удалить».
- Форма задания получает поле «Важность».
- Когда отмечен последний шаг, а задание не выполнено, под списком появляется строка «Все шаги готовы. Отметить задание выполненным?» с кнопкой. Статус сам не меняется. Если шаг потом снимают, строка пропадает.
- Порядок «По важности»: сначала «Срочный», потом «Важный», потом «Обычный», внутри — по сроку.

## Проверка

Автоматические проверки (xUnit, `WebApplicationFactory`):

- Приложение: `manifest.webmanifest` и `sw.js` отдаются со своими типами; все файлы из списка оболочки в `sw.js` существуют в `wwwroot/`; воркер содержит исключения для `/api`, `/health`, `/calendar.ics`.
- Календарь: создание, перевыпуск (старый ключ — `404`), выключение, неверный ключ — `404` без различий; в ленте нет выполненных заданий и чужих; экранирование и сворачивание строк; стабильный `UID`; ключ в базе только хешем; токен API на `/api/calendar` — `401`; лимит `429`; миграция сохраняет старые данные.
- Подзадачи: добавление, правка, отметка, удаление, порядок; лимит 30; чужое задание — `404`; удаление задания каскадом удаляет шаги; `PUT` задания не стирает шаги и без `priority` не меняет важность; `/api/v1` отдаёт поля и не принимает подзадачи; миграция сохраняет старые задания с важностью «Обычный».

Проверка глазами в Edge (Playwright, `channel="msedge"`): установка приложения и запуск окном на `localhost`; отключение сети — оболочка открывается, виден экран «Повторить подключение»; диалог «Календарь» (создание, копирование, перевыпуск); подписка на настоящую ленту из Edge не проверяется, разбор ленты проверяется тестами; шаги, предложение завершить задание и сортировка на ширине 320, 390 и 1440 пикселей.

Не проверяется: iPhone, Android, Google Календарь и Outlook как подписчики, экранные читалки.

## Риски

| Риск | Что делаем |
|---|---|
| Сервис-воркер закэшировал старую оболочку | Порядок «сначала сеть»; воркер проверяется на отсутствие `/api` в кэше |
| Секрет ленты попал в журнал прокси | `RequestLogging` пишет без query; в README предупреждение про журнал Caddy |
| Подписка в календаре держит отозванный адрес | После отзыва всегда `404`, календарь покажет ошибку подписки |
| Миграция на базе с данными | Тест миграции по образцу `ImportKeyMigrationTests`, откат невозможен, но миграция только добавляет |
| Рост ответа `/api/assignments` из-за шагов | Не больше 30 шагов на задание, при этом названия до 140 символов; для личного списка допустимо |

## Готово, когда

- Приложение ставится в Edge на `localhost`, без сети открывается оболочка, `/api` в кэш не попадает.
- Лента отдаёт события невыполненных заданий, отзывается перевыпуском и выключением, неверный ключ всегда `404`.
- Шаги добавляются, отмечаются, переставляются и удаляются; при всех готовых шагах предлагается завершить задание; важность видна и сортирует список.
- Все старые 220 проверок и новые зелёные, сборка без предупреждений.
- README и `/api/docs` описывают новое, версия 0.7 в README.
