# Роли и группы: владелец, староста, студент и гость

Статус: идея, спецификация от 9 ноября 2026 года, версия 0.8. Ничего не собиралось и не проверялось: это описание того, что будем делать. План: `docs/plans/роли-и-группы.md` (пишется после одобрения этой спецификации).

Связано: [README](../../README.md), [спецификация версии 0.7](календарь-подзадачи-и-pwa.md), [спецификация версии 0.5](эксплуатация-и-api.md), [модели и база](../../Models.cs), [эндпоинты заданий](../../Endpoints/AssignmentEndpoints.cs), [эндпоинты шагов](../../Endpoints/SubtaskEndpoints.cs), [аккаунты](../../AuthEndpoints.cs), [календарная лента](../../Calendar/CalendarEndpoints.cs).

## Идея

Сейчас «Зачёт» личный: каждый видит только свои предметы и задания. Но учебная группа живёт общим расписанием, и один человек (староста) обычно знает сроки за всех. Версия 0.8 добавляет общее пространство группы и четыре роли.

| Роль | Кто это | Что делает |
|---|---|---|
| Владелец | Автор приложения, в базе один-два человека | Создаёт группы, назначает и снимает старост, видит все группы и всех пользователей |
| Староста | Студент, которого назначил владелец | Всё, что студент, плюс ведёт предметы, задания и сроки своей группы, подтверждает заявки, выдаёт ссылку для гостей |
| Студент | Любой вошедший аккаунт | Видит задания своей группы и свои личные, отмечает выполнение, добавляет себе шаги |
| Гость | Человек без аккаунта | Открывает страницу группы по ссылке или подписывается на ленту `.ics` группы, только чтение |

Личные предметы и задания остаются как были: у каждого аккаунта они свои, группа к ним не прикасается.

## Что не входит

- Несколько групп у одного студента: студент состоит ровно в одной группе (или в ни одной).
- Напоминания в Telegram о заданиях группы, импорт из Obsidian в группу, групповые задания в `/api/v1`: токены API и Telegram остаются личными.
- Права «преподаватель», «заместитель старосты», разные права у разных старост: все старосты группы равны.
- Переписка, комментарии к заданиям, вложения, уведомления «вас приняли в группу»: студент увидит новый статус, когда откроет раздел «Группа» или обновит страницу.
- Общая отметка «группа выполнила»: отметки только личные.
- Перенос задания между личным списком и группой, перенос студента из группы в группу одним действием (нужно выйти и подать заявку).
- Отзыв права владельца через интерфейс: владельца назначает и снимает только команда на сервере.
- Удаление аккаунтов (его в приложении и так нет).

## Решения по умолчанию

| Вопрос | Решение |
|---|---|
| Где хранится «владелец» | Булева колонка `AspNetUsers.IsOwner`, а не роль Identity: роль Identity попадает в cookie и устаревает до следующего входа, а флаг читается из базы на каждом запросе |
| Как назначается первый владелец | Командой `--make-owner <почта>` на сервере (рядом с `--create-account`); через интерфейс и API владельца сделать нельзя |
| Кто выдаёт и снимает старост | Только владелец |
| Что даёт «владельцу» работа с заданиями группы | Ничего сверх управления: чтобы вести задания группы, владелец назначает старостой себя |
| Что видит студент до подтверждения заявки | Только личное; группа ему не видна |
| Название группы | 1–60 символов, уникально без учёта регистра |
| Чужая группа, чужое задание, нет прав | Всегда `404`, как и сейчас для чужих данных; ответ не различает «нет» и «нельзя» |
| Конфликт состояния (уже в группе, нельзя снять старосту) | `409` с понятным сообщением |
| Ссылка гостя | Один секрет на группу, 32 случайных байта, 43 символа base64url, в базе только SHA-256; новая выдача отзывает старую |
| Что видит гость | Название группы и задания из окна по сроку: предмет, название, описание, срок, важность. Ни имён, ни почт, ни отметок |
| Какие задания в ленте и на странице гостя | Срок не раньше, чем 7 дней назад; не больше 500 штук по возрастанию срока |
| Что стирается, когда студент уходит или его убирают | Его отметки и его шаги по заданиям этой группы |
| Статус группового задания, который хранится в самом задании | Не используется: статус каждого студента лежит в `GroupProgress`, а при чтении подставляется его собственный |

## Права

| Действие | Гость | Студент | Староста | Владелец |
|---|---|---|---|---|
| Видеть задания и сроки группы | по ссылке | своей группы | своей группы | только как участник группы |
| Отмечать выполнение и вести свои шаги по заданиям группы | нет | да | да | как участник |
| Личные предметы и задания | нет | да | да | да |
| Создавать и менять предметы, задания и сроки группы | нет | нет | своей группы | как староста, если назначил себя |
| Подтверждать, отклонять заявки; убирать студентов | нет | нет | своей группы | любой группы |
| Выдавать, перевыпускать и отзывать ссылку гостя | нет | нет | своей группы | любой группы |
| Создавать, переименовывать, удалять группы | нет | нет | нет | да |
| Назначать и снимать старост | нет | нет | нет | да |
| Видеть список групп и пользователей с почтами | нет | названия групп для выбора | участников своей группы | все |

Права проверяет сервер на каждом запросе по базе: роль не берётся из cookie и из тела запроса. Если владелец снял старосту, со следующего же запроса тот перестаёт быть старостой.

## База

Новые таблицы:

| Таблица | Поля | Заметки |
|---|---|---|
| `Groups` | `Id`, `Name` (до 60), `NameKey` (верхний регистр, уникальный индекс), `GuestKeyHash` (64 символа или `NULL`, уникальный индекс), `GuestKeyCreatedAt` | `NULL` в `GuestKeyHash` значит «ссылки нет» |
| `GroupMembers` | `Id`, `GroupId`, `UserId`, `Role` (0 — `Student`, 1 — `Head`), `Status` (0 — `Pending`, 1 — `Active`), `CreatedAt` | Уникальный индекс по `UserId`: один человек состоит в одной группе или подал одну заявку. Удаление группы или аккаунта удаляет строки каскадом |
| `GroupProgress` | `Id`, `AssignmentId`, `UserId`, `Status` (как у `Assignment.Status`) | Уникальный индекс `(AssignmentId, UserId)`. Нет строки — значит `Todo`. Каскад по заданию и по пользователю |

Изменения в существующих таблицах:

| Таблица | Что меняется |
|---|---|
| `AspNetUsers` | Колонка `IsOwner`, по умолчанию 0 |
| `Subjects` | `OwnerId` становится необязательным; новая колонка `GroupId` (внешний ключ на `Groups`); `CHECK` — задано ровно одно из `OwnerId`, `GroupId`; уникальный индекс `(GroupId, NameKey)` рядом с прежним `(OwnerId, NameKey)`; альтернативный ключ `(Id, GroupId)` |
| `Assignments` | То же: `OwnerId` необязательный, новая `GroupId`, `CHECK` на «ровно одно»; второй составной внешний ключ `(SubjectId, GroupId)` к предмету, рядом с прежним `(SubjectId, OwnerId)`: задание группы не может ссылаться на предмет другой группы или на личный предмет |
| `Subtasks` | Колонка `UserId` (необязательная, внешний ключ на пользователя, каскад). `NULL` — шаг личного задания; заполнено — личный шаг студента по заданию группы |

Выбор «владелец или группа» сделан, а не «владелец плюс группа», чтобы существующие запросы `OwnerId == я` (личный список, личная лента `.ics`, Telegram, импорт, `/api/v1`) сами не видели ничего группового и их не пришлось переписывать с оглядкой на утечки.

Миграция добавляет таблицы и колонки и пересобирает `Subjects` и `Assignments` (SQLite не умеет менять «обязательность» колонки иначе). Все существующие строки получают `GroupId = NULL` и остаются личными. Откат не предусмотрен; перед обновлением базы стоит копировать файл, как и раньше.

Удаление группы делается кодом в одной транзакции: задания, потом предметы, потом сама группа (участники, отметки и шаги уходят каскадом), потому что связь «задание — предмет» запрещает удалять предмет раньше задания.

## Первый владелец

`dotnet StudyTracker.dll --make-owner <почта>` ставит `IsOwner` у существующего аккаунта. Неизвестная почта: сообщение «Аккаунт не найден.» и код выхода 1. Повторный вызов безвреден. В Docker: `docker compose run --rm app --make-owner <почта>`. Снять права владельца командой не предусмотрено в этой версии (можно правкой базы).

## Адреса `/api` (cookie и CSRF; токен API на них не принимается — `401`)

### Состояние аккаунта

`GET /api/auth/me` теперь возвращает `{ id, email, isOwner, group }`, где `group` — `null` или `{ id, name, role: "Student" | "Head", status: "Pending" | "Active" }`. Приложение читает его при старте и при открытии раздела «Группа».

### Студент

| Метод и адрес | Что делает |
|---|---|
| `GET /api/groups` | Список `{ id, name }` для выбора, по алфавиту |
| `POST /api/groups/{gid}/join` | Заявка: `201` и `group` в статусе `Pending`. Если у аккаунта уже есть строка в `GroupMembers` (заявка или членство): `409` «Вы уже состоите в группе или подали заявку.» |
| `DELETE /api/group/membership` | Отмена заявки или выход: `204`. Стирает его отметки и шаги по заданиям группы. Староста: `409` «Старосту снимает владелец.» |

### Староста группы `gid` и владелец

Всё в этом блоке: не староста этой группы и не владелец — `404`.

| Метод и адрес | Что делает |
|---|---|
| `GET /api/groups/{gid}/members` | `[{ userId, email, role, status }]`: заявки и участники |
| `POST /api/groups/{gid}/members/{userId}/approve` | `Pending` → `Active`: `200`. Если заявки нет — `404`, если уже `Active` — `409` |
| `DELETE /api/groups/{gid}/members/{userId}` | Отклоняет заявку или убирает студента: `204`. Старосту может убрать только владелец (иначе `409`). Стирает отметки и шаги этого человека по заданиям группы |
| `GET /api/groups/{gid}/guest-link` | `{ "exists": true, "createdAt": "…" }` или `{ "exists": false }` |
| `POST /api/groups/{gid}/guest-link` | Выдаёт или перевыпускает: `201` и `{ "key": "…", "createdAt": "…" }`; старый ключ перестаёт работать. Показывается один раз |
| `DELETE /api/groups/{gid}/guest-link` | Выключает: `204`, повтор тоже `204` |

### Владелец

Не владелец — `404` на всё в блоке.

| Метод и адрес | Что делает |
|---|---|
| `GET /api/owner/groups` | `[{ id, name, members, pending, heads: [{ userId, email }] }]` |
| `POST /api/owner/groups` | `{ "name": "…" }` → `201`. Название пустое или длиннее 60 — `400`; уже есть — `409` «Такая группа уже есть.» |
| `PUT /api/owner/groups/{gid}` | Переименование, те же проверки |
| `DELETE /api/owner/groups/{gid}` | Удаляет группу со всем содержимым: `204` |
| `GET /api/owner/users?q=` | До 50 пользователей по почте (без учёта регистра, подстрока), по алфавиту: `{ id, email, isOwner, group }` |
| `PUT /api/owner/groups/{gid}/heads/{userId}` | Делает старостой: `200` и участник. Если человека нет в группе, добавляет его сразу `Active`; если он студент или заявитель этой группы — повышает до `Active` старосты; если состоит в другой группе — `409` «Состоит в другой группе.» |
| `DELETE /api/owner/groups/{gid}/heads/{userId}` | Снимает: старосту делает обычным студентом, `200`. Если человек не староста этой группы — `404` |

### Предметы, задания и отметки

Существующие адреса расширяются, новых путей почти нет.

| Метод и адрес | Что меняется |
|---|---|
| `GET /api/subjects`, `GET /api/assignments` | Возвращают личное и всё из группы, где аккаунт `Active`. У каждой записи есть `groupId` (`null` у личных). У группового задания `status` и `subtasks` — собственные у этого студента, остальные студенты не видны. Для `Pending` и без группы — только личное |
| `POST /api/subjects` | Необязательное поле `groupId`. Есть — нужен староста этой группы (иначе `404`), предмет создаётся в группе; нет — личный, как раньше |
| `DELETE /api/subjects/{id}` | Групповой предмет удаляет староста его группы; правила про «сначала задания» те же |
| `POST /api/assignments` | Необязательное поле `groupId`, то же правило. Предмет должен быть из той же группы, иначе `404`. Поле `status` у группового задания игнорируется |
| `PUT /api/assignments/{id}` | Групповое задание правит староста его группы. `groupId` в теле либо не передан, либо равен группе задания; иначе `400` «Нельзя перенести задание между личным списком и группой.» |
| `DELETE /api/assignments/{id}` | Групповое задание удаляет староста его группы; отметки и шаги уходят каскадом |
| `PUT /api/assignments/{id}/progress` | Новый адрес, только для групповых заданий: `{ "status": "Todo" | "InProgress" | "Done" }` → `200` с заданием. Нужно быть `Active` в группе задания. Личное задание — `404` |

### Шаги

Адреса те же, что в 0.7. Для личного задания всё как было. Для группового нужно быть `Active` в его группе; шаг создаётся с `UserId` = аккаунт, видно, правится и переставляется только своё, чужой шаг — `404`. Предел 30 шагов считается по своим шагам.

### `/api/v1` и прочее личное

В `/api/v1` групповых данных нет, а `groupId` в теле запроса даёт `400` («В токене API группы не поддерживаются.»), чтобы задание не создалось личным молча. Личная лента `.ics`, Telegram и импорт из Obsidian групповых заданий не видят: они выбирают по `OwnerId`, а у групповых он пуст.

## Гость

Все три адреса вне `/api`: без cookie и без CSRF. Лимит тот же, что у личной ленты (60 запросов в минуту с адреса, дальше `429`). Ключ неверный, пустой или отозванный — одинаковый `404` без тела. Заголовки: `Cache-Control: no-store`.

| Адрес | Что отдаёт |
|---|---|
| `GET /public/group?key=<секрет>` | JSON `{ name, assignments: [{ subject, color, title, description, dueDate, priority }] }` по правилам окна из таблицы решений |
| `GET /group.ics?key=<секрет>` | Лента `.ics` по образцу личной: `UID:group-task-<Id>@zachet`, `SUMMARY:Предмет: Название`, весь день срока, описание не включается, `X-WR-CALNAME:<название группы>` |
| `GET /g.html` | Статичная страница, читает секрет из `#фрагмента` адреса и запрашивает `/public/group`. Секрет во фрагменте не попадает ни на сервер, ни в журнал, ни в `Referer` |

Староста раздаёт ссылку `<origin>/g.html#<секрет>` и адрес ленты `<origin>/group.ics?key=<секрет>`: оба строятся из одного ключа и показываются один раз. Ключ в query у ленты (а не в пути) по той же причине, что у личной: журнал запросов пишет путь без query. Ссылку можно переслать кому угодно, это сказано в интерфейсе: гость видит всё, что видит страница.

## Интерфейс

- Кнопка «Группа» в навигации (всем вошедшим) открывает диалог по образцу «Календарь»:
  - без группы: список групп и кнопка «Подать заявку»;
  - заявка отправлена: «Заявка в группу «…» ждёт подтверждения» и «Отменить заявку»;
  - студент: название группы и «Выйти из группы» с подтверждением;
  - староста: ещё две вкладки. «Участники»: заявки с кнопками «Принять» и «Отклонить», список с «Убрать». «Для гостей»: создать, перевыпустить и отозвать ссылку, адреса страницы и ленты в полях только для чтения с кнопкой «Скопировать», предупреждение, что показ один раз и ссылку можно переслать.
- Кнопка «Владелец» (только при `isOwner`): группы (создать, переименовать, удалить с подтверждением, видно число участников и заявок), пользователи с поиском по почте, кнопки «Назначить старостой» и «Снять».
- Формы предмета и задания: у старосты появляется переключатель «Личное / Группа»; при «Группа» список предметов показывает только предметы группы. У остальных переключателя нет. Группа у существующего задания не меняется.
- Список заданий: у групповых значок и подпись «Группа», фильтр «Все / Личные / Группа». Студенту у групповых заданий нет кнопок «править» и «удалить»; кнопка статуса вызывает `PUT …/progress`. Шаги работают как у личных.
- После выхода из аккаунта состояние диалогов стирается (событие `account-cleared`); тексты через `textContent`, без inline-скриптов. Новые скрипты (`groups.js`, `g.js`) добавляются в `index.html` или `g.html`, в `check.yml`, а `groups.js` ещё и в оболочку `sw.js`.
- Страница гостя `g.html`: заголовок с названием группы и список заданий по срокам, без кнопок и входа; при неверной ссылке — «Ссылка недействительна».

## Проверка

Автоматические проверки (xUnit, `WebApplicationFactory`), по группам:

- Права и изоляция: студент не создаёт и не правит групповое (`404`); староста группы A не трогает участников, ссылку, предметы, задания и отметки группы B (`404`); заявитель (`Pending`) ничего не видит из группы; не владелец на `/api/owner/*` — `404`; токен API на новых адресах — `401`; без CSRF-токена изменения отклоняются.
- Роли «на лету»: после снятия старосты следующий запрос уже `404`; после подтверждения заявки студент сразу видит задания.
- Заявки и состав: одна группа на аккаунт (`409` на вторую заявку), одобрение, отклонение, выход (стирает отметки и шаги), староста не может уйти (`409`), владелец назначает и снимает; повышение из другой группы — `409`.
- Задания группы: у студента `status` свой, у соседа свой, староста чужие не видит; шаги студента не видны соседу и старосте; лимит 30 шагов считается по своим; задание группы нельзя привязать к чужому или личному предмету; `groupId` в PUT, отличающийся от группы задания, — `400`.
- Личное не утекает: группы нет ни в `/api/v1`, ни в личной ленте `.ics`, ни в выборках Telegram и импорта; `groupId` в `/api/v1` — `400`.
- Гость: страница и лента показывают окно «−7 дней, до 500» и не показывают почт и отметок; неверный и отозванный ключ — одинаковый `404`; в базе ключ только хешем; перевыпуск отзывает прежний; лимит `429`; экранирование и `UID` ленты.
- Удаление группы убирает всё: участников, предметы, задания, отметки, шаги.
- Команда `--make-owner`: ставит флаг, неизвестная почта — код 1.
- Миграция на базе со старыми данными: личные предметы и задания остаются с `GroupId = NULL`, шаги и важность на месте; `CHECK` отвергает строку без владельца и группы одновременно и строку с обоими. Тест отката миграций (`NotificationMigrationPreservesAccounts`) дополняется удалением новых таблиц и колонок.

Проверка глазами в Edge (Playwright, `channel="msedge"`): весь путь на живом сервере — владелец создаёт группу и назначает старосту, студент подаёт заявку, староста её принимает и добавляет задание, студент отмечает его и добавляет шаг, гость открывает `g.html#…` без входа; диалоги на ширине 320, 390 и 1440 пикселей.

Не проверяется: подписка на `group.ics` из Google, Apple и Outlook Календаря, iPhone и Android, экранные читалки.

## Риски

| Риск | Что делаем |
|---|---|
| Утечка данных группы между группами и студентами: самое опасное место версии | Один помощник прав на все новые и изменённые эндпоинты, `404` на любой отказ, тест на каждую пару ролей из списка выше |
| Групповые задания попадают в личные выборки | Групповые записи имеют `OwnerId = NULL`; тесты на ленту, Telegram, импорт и `/api/v1` |
| Пересборка `Subjects` и `Assignments` теряет данные или ломает связи | Тест миграции на базе со старыми строками, шагами и важностью; ручная копия базы перед обновлением; `PRAGMA foreign_key_check` в тесте |
| Ссылка гостя ушла посторонним | Перевыпуск и отзыв в один клик; ключ во фрагменте адреса, не в журнале; предупреждение в интерфейсе |
| В открытой регистрации любой аккаунт видит названия групп | Регистрация в Production закрыта; названия — единственное, что видно (`id` и `name`); участники и задания не видны |
| Нет владельца: никто не создаст группу | В README и в сообщении `--create-account` напоминаем про `--make-owner` |
| Студент не видит подтверждение, пока не обновит страницу | Состояние перечитывается при открытии раздела «Группа»; уведомлений нет (не входит в версию) |

## Готово, когда

- Владелец (команда `--make-owner`) создаёт группу, назначает старосту; студент подаёт заявку, староста принимает; староста ведёт предметы и задания группы; студент видит их вместе с личными, отмечает выполнение и добавляет шаги, не видя чужих отметок.
- Гость открывает страницу группы по ссылке и подписывается на ленту, не входя; неверная и отозванная ссылка всегда `404`.
- Личные данные, `/api/v1`, личная лента, Telegram и импорт работают как раньше и групповых заданий не видят.
- Все старые 265 проверок и новые зелёные, сборка без предупреждений, миграция сохраняет старые данные.
- README и `/api/docs` описывают новое, версия 0.8 в README.
